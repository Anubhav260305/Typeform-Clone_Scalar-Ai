Executive Summary
The existing backend adheres strictly to the prescribed 5-tier architecture: Route → Service → Repository → SQLAlchemy ORM → SQLite. The core form management flow (Create, Read, List, Update title, Delete) and collision-resistant slug generation are operational. However, the repository contains no question models or endpoints, no response submission or storage logic, no publish/unpublish workflow, no analytics aggregation, and no frontend application.

F. Architectural Problems & Risks

1. Premature Commits in Repository Layer (Unit of Work Risk) Medium Risk
FormRepository.create(), update(), and delete() call self.db.commit() directly. When composite operations are introduced (such as creating a form with questions, or saving a submission with multiple answers), committing inside individual repository methods breaks atomic transactions. If step 2 fails, step 1 cannot be rolled back.
Mitigation: Keep repository methods for staging changes, and coordinate commit/rollback boundaries in the service layer or via a transactional context manager.
2. SQLite Foreign Key Enforcement & Cascading Deletes Medium Risk
SQLite disables foreign key enforcement by default unless explicitly activated via PRAGMA foreign_keys = ON; upon engine connection. Without this and explicit SQLAlchemy cascade="all, delete-orphan", deleting a form could leave orphaned questions and responses.
Mitigation: Add a SQLite connect event listener in connection.py to execute PRAGMA foreign_keys = ON, and declare cascade options on parent relationships.
3. Rigid FormUpdate Schema & Testing Dependencies Design Consideration
FormUpdate only permits title: str. Updating form status (publish / unpublish) or description will require broadening the schema to optional fields. Additionally, requirements.txt is missing httpx and pytest, causing fastapi.testclient.TestClient to fail during test execution.

G. Recommended Next Steps & Roadmap

Phase 1: Expand SQLAlchemy Models & Database Schema Data Layer
Create Question model (with title, description, type, required, order_index, options as JSON/relationship) and Response / Answer models with cascading delete rules. Enable foreign keys in SQLite.
Phase 2: Question & Response Repositories & Services Logic Layer
Add QuestionRepository, QuestionService (handling position indexing, reordering, and type validation), and ResponseRepository, ResponseService (handling atomic submission, answer validation per type, and basic analytics aggregation). Add publish/unpublish methods to FormService.
Phase 3: Expose REST Endpoints API Layer
Implement builder routes (question CRUD & reordering), public respondent routes (GET /api/public/forms/{slug} and POST /api/public/forms/{slug}/submit), and analytics routes (GET /api/forms/{form_id}/responses and /analytics).
Phase 4: Seed Script & Verification Verification
Write a clean seed script populating sample forms with all 8 question types and test submissions for rapid verification and evaluation.
